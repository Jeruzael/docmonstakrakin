## 2. Product outcome and client capability boundary

The proposed product is an engineering control plane usable from an external coding client, an approved direct local adapter, GitHub-mediated work, an approved local model or manual copy/paste. A DMK-held model API key is not required for external-client or manual workflows. Clients may use their own separately authorized execution/inference facilities; DMK must not infer their tools, authentication, subscriptions, event feeds, wakeup, cost telemetry or persistent connectivity from a client name. A versioned capability descriptor records actual supported operations, transport, authentication, message acknowledgment, cancellation and event observations. Unsupported capability is explicitly unavailable; manual compile/import remains useful.

One action contract and one server policy evaluation path govern all transports. A future adapter translates envelopes, not permissions. Direct/local/GitHub/manual paths cannot create separate policy engines. User-pasted JSON is a user import with declared external provenance, not an authenticated live agent session. GitHub account, commit signature, workflow actor and agent identity are distinct; a GitHub actor is not evidence of an independently appointed human approver.

Candidate envelope fields include schema/version, project/task, stable server-resolved principal/client/session, sponsor/delegation and policy revisions, operation, expected state/criteria revisions, content/body digest, scoped idempotency token, source manifests, skill receipt references and acknowledgment correlation. These are design fields, not existing endpoints. Validate schema and scope before policy/action admission. A successful receipt identifies the committed revision and effect, while queued, rejected, uncertain and acknowledged delivery remain distinguishable.

Bind `(project, server-resolved actor, operation, token)` to a separate immutable body digest. Same token/same body returns the prior local result; same token/changed body rejects without new effects. Reject stale CAS before changing state. Atomically commit authorized action, audit, outbox and acknowledgment intent. Retry/reconnect reauthorize against current grants, skills, policy, content and expiry, preserving operation identity and history. Crash before/after commit/send/ack must recover visibly; local exactly-once effects do not promise once-only external execution or billing. Bound retries, collaboration hops, fanout, time and budgets; exhaustions escalate to authorized humans rather than continuing loops.

## 3. Conversation and accepted project knowledge

Conversation can create a new project or attach to an existing project after an authorized identity/match review. Reuse an existing stable project ID when appropriate; uncertain matches ask a scoped question rather than silently duplicating or merging projects. Extract proposed goals, constraints, requirements, decisions, risks, questions and tasks into linked structured records. Record source conversation/message references, author/recipient, purpose, provenance, affected version, and the human acceptance/disposition. Only accepted records join canonical project knowledge. Raw private chat, private scratchpads and hidden reasoning are not copied into shared knowledge, prompts or documentation. Accepted summaries still inherit source policy and require authorized disclosure.

For ordinary managed projects, DMK governs accepted structured knowledge, Git governs source code/revisions, CI governs execution observations, and documents are versioned projections with source links and freshness. Do not imply that a chat answer is code truth or that a Git edit is an accepted DMK decision. The self-project is special: **DMK-205 retains `MASTER_WBS.yaml` authority over self-project WorkItem projections**. Reversing that direction requires a separately governed migration defining custody, exact scope, history, CAS/cutover, rollback and human approval; ordinary-project design is no shortcut.

## 4. Trusted skills, prompt registry and per-operation admission

Extend existing compiler and reusable prompt/library assets rather than introducing a second prompt system. The proposed registry stores stable asset ID, description, immutable version/content digest, applicability, trust/source, owner, allowed operations, required dependencies, policy compatibility, revocation and replacement history. Untrusted repository text, skill descriptions and returned model content carry no authority. Registration and trust decisions are authorized operations, not consequences of retrieval or model claims.

Before **each operation**, consult the current applicable skill descriptions and pinned required versions; acquire only needed content within access policy and emit an admission receipt binding operation/body, task/criteria revision, principal/client/session, policy, skill versions/digests, time and expiry. Reconsult/refresh if task, required skill, policy, permissions, asset versions or operation content changes. Revoke receipts when underlying trust/grants are revoked. Retrieval/read receipt proves delivery/consultation only; it does not prove understanding, competence or compliance. Independent server validation still enforces scope and action rules.

Unauthenticated discovery exposes only explicitly public minimal service availability, protocol/schema versions and authentication-required capability metadata. It cannot disclose project existence, identity, tasks, private policy, skill descriptions/content, membership or secrets. Bootstrap reads are explicit minimal operations: authenticated current membership may read permitted catalog descriptions, required skill content and current policy needed to request a receipt, under a fixed bootstrap allowlist. They do not require their own recursively issued receipt and cannot mutate work, enroll identity, grant authority or read forbidden content. Unknown applicability/version/trust fails admission with a concrete question or blocked reason. Registry EXT-CAND-03 owns assets; DMK-209 owns the single admission control, coordinated with DMK-210/213. No duplicate admission engine is retained from EXT-CAND-04.

Compiler extension packages carry current task/criteria/state revisions, linked accepted knowledge, required skill versions, policy and allowed operations, editable-target manifest, expected response schema and required acknowledgment. Validate returned structured responses against the pinned scope/schema and current revisions, then record attributed proposal disposition/acknowledgment. Stale or unauthorized changes fail; no implicit overwrite or human-approval import. DMK-190 retains its verified original schema 1.1 criteria; the extension is new linked work (absorbed EXT-CAND-05).

## 5. Continuous typed clarification

Questions may arise during any phase or run. Support short/long text, single/multiple selection, radio, dropdown, yes/no/unknown, numeric/date/range, repeatable groups, table and evidence inputs, with versioned validation and accessibility. Every question includes provenance, reason/purpose, constraints, branch condition, affected work/criteria, intended authorized recipient, severity and answer validity. Reuse accepted answers only when scope and freshness match; deduplicate equivalent open questions without losing source links. Changed assumptions reopen affected questions and preserve prior answers, reasons, decisions and history.

Block only affected work and downstream dependencies; unrelated work can proceed under its own policy. Notify only authorized recipients with source-safe metadata. A response can resolve an explicitly scoped blocker after validation; it is not a release approval, independent human vote, change of authority or blanket authorization. DMK-020 owns question semantics; DMK-027 owns renderer/accessibility and DMK-033 lifecycle impact, preserving existing canonical enums.

## 6. Task collaboration, evidence and conflict recovery

Authorized agents may atomically claim/self-assign, start, report progress, ask for clarification, hand off, request review and recover a conflicted claim within explicit grants. Persist claimant identity/session, task revision, fencing/lease semantics, expected revision and audit. Race two claims and accept one; reject stale task/grant/lease attempts. A disconnect changes presence, not completion or automatic claim release. Explicit claim expiry/recovery policy is separate, and uncertain work remains visible. Preserve the canonical WorkItem lifecycle and enum meaning; activity labels do not invent lifecycle transitions. Agents never occupy independently required human quorum seats.

Evidence binds exact criteria revision, source/configuration revision, environment/tool versions, producer identity and provenance, execution scope, observation time, inputs/results, digest/artifact reference and reviewer disposition. Keep failed, partial, NOT_RUN and UNAVAILABLE results. Criteria/code/config/policy changes stale the affected evidence; unrelated evidence retains its own scope. A hash demonstrates byte identity/integrity, not source authenticity, producer independence or successful execution. Distinguish agent-reported, externally observed and technically verified claims, with explicit uncertainty and freshness. Preserve independent human authority even when an independent agent review passes.

DMK-201 owns ordinary-project decision/document synchronization and transactional conflicts. EXT-CAND-02 owns the GitHub project-command bridge/outbox/ack lifecycle; DMK-179 owns scoped Git operations and DMK-180 issue/tracker projections. Carry common contract, source/target revisions, last acknowledgment, retry attempts and conflict state. Refuse stale overwrites, divergent authorities, replayed commands, changed-body tokens and ambiguous delivery. Reconcile with preserved history and authorized disposition rather than last-writer-wins. EXT-CAND-06 is absorbed by DMK-201/205, not a competing authority service.

## 7. Durable workplace identity and truthful presence

Maintain a durable agent profile and separate client, authenticated session, assignment, activity, result and event identities. Reconnect the same authorized identity without duplicate profiles; support multiple sessions explicitly and revoke them independently. DMK-213 owns principal/sponsor/delegation identity; EXT-CAND-07 owns durable profile/session projection, presence and event history. Avatars and role labels convey no permissions.

Actual source events may show entered, task activity, blocked, awaiting review, resting and inactive. Store event source, observed/reported time, server receipt, validity and projection version. The user-requested configurable rest-exit range is **10–15 minutes**, with **15-minute default expiry a PROPOSAL**, pending product/operational validation. Silence may mean disconnected or unknown; it cannot mean completed, claim released, remote termination or verified progress. Manual sessions have explicit last-updated/unknown liveness rather than synthetic heartbeat. Never invent progress percentages, model thoughts, durations, tokens or costs; expose unavailable/unverified measurements honestly. Existing demo metrics remain `SIMULATED_DEMO`.

Simple is the required usable view; optional 2D uses the same authorized event stream, selected identity/task/thread, provenance and uncertainty. No visual mode mutates authority or reconstructs a different task state. Keyboard, screen reader, reduced motion, responsive layout and no-WebGL Simple fallback are required. **3D is DEFER**, not an implementation slice here. EXT-CAND-08 is absorbed into07; v0.3 UX-05 stays historically proposed.

## 8. Durable chat, mentions and human blockers

EXT-CAND-09 owns durable project/task/artifact threads, human/agent messages, mentions, blocker conversations and delivery states. Persist message/event IDs, lineage, recipients, queue and per-recipient delivery acknowledgment. Distinguish **queued / delivered / read / acted**; receipt is not action and a mention/wakeup request is not a guarantee a client will run. Agent reply/delegation loops have bounded hops/rate/time/budget, idempotency, deduplication and human escalation.

Derived messages inherit highest classification **and the intersection of all contributing source ACLs**, including uncited inputs, plus current target policy and denies. Evaluate read and discover-existence separately on send, queue, delivery, render, search, export and access after revocation. A discover-denied recipient receives no pointer, count, unread badge, notification, title, avatar caption or timing-sensitive activity detail. Equal data classes with disjoint source readers must remain disjoint. Reauthorize queued notifications at delivery and historical content after ACL change; cache invalidation is part of the contract. `@everyone` is the dynamically authorized intersection. Human answers do not grant agent authority or release approval.

## 9. Continuous security and exact release qualification

Link threats, controls, security questions, tests, findings, remediation and evidence coverage to affected requirements/tasks/releases. Show scope, gaps and freshness rather than claiming all vulnerabilities are detected. Explicitly authorize penetration-test targets, techniques, environment, time, data handling and stop conditions; repository read access does not authorize attacks. DMK-038 risk, DMK-041 exceptions, DMK-199 tests and DMK-206 evidence absorb EXT-CAND-10 with each criterion assigned once.

Release assessment binds an exact candidate revision and configuration, environment/provenance, evidence freshness, open blockers/findings, scoped exceptions with accountable human/expiry, dependency status and rollback readiness. Unknown, failed, NOT_RUN and UNAVAILABLE do not become PASS. Changes invalidate the affected assessment/exception; no broad carryover from a different candidate. DMK-202 owns release decision projection; Gate 7 remains a human decision under existing authority. Scoped repository read/write access does not imply shell, secrets, deployment, production credentials or release rights. Activate each new transport/agent route only after exact identity/delegation/admission/durability/ACL and supported-environment tests are accepted separately.
