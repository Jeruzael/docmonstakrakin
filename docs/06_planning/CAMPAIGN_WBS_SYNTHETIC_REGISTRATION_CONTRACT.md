## Implemented boundary

`scripts/lib/syntheticWbsRegistration.ts` composes the existing offline governance envelope, strict v2 receipt normalization, unchanged v2 cryptographic registration verifier and unchanged canonical transaction preview. It accepts only `SYNTHETIC_REGISTRATION/1` and a separately supplied `TESTONLY_PUBLIC_ROOTS` acquisition interface. A request cannot supply its own roots, policy, role profile, clock, Git provenance or replay list. The host supplies the acquisition callback and independently pinned hash of the public governance/witness/clock anchors. There is no default source, environment fallback, production mode, root enrollment or automatic root rotation.

The adapter snapshots bounded inert data and request Buffers. It verifies the separately signed acquisition message using the envelope's independent witness key with the domain `DOCMONSTAKRAKIN/TESTONLY_WBS_ACQUISITION/1` plus LF and canonical JSON. The message binds the request byte digests, envelope digest, exact reviewed Git context, protected pre-state, proposed applied identity, state/ledger hashes, time and epoch/revocation/clock/checkpoint sequences. It requires the applied state's first parent to equal the protected base and permits at most two applied parents. This models an authenticated acquisition contract; fixture signatures do not authenticate a real GitHub authority or physical person.

`SYNTHETIC_REGISTRATION/1` selects ordinary **Security Officer + Lead Architect**, or elevated **Security Officer + Lead Architect + Independent Human Approver**, exclusively through the verified envelope's profile and exact v2 policy. Existing purpose separation, real Ed25519 signatures, one-to-one person/principal assertions, conflicts, custody, epoch succession, revocation, witness and clock checks remain mandatory. Gio's two charter responsibilities count as one human. No key or account count establishes person independence.

Durable prior-envelope identity, policy digest/version, epoch, root identity/version and revocation sequence must match the acquired predecessor exactly. Current floors and monotonic time cannot roll back. Missing current evidence fails even when historical verification succeeds. The original two-role historical continuity verifier and DMK-196/197/208 contracts are unchanged; their original 27-item scope is not widened. Elevated compatibility exists in this **new versioned synthetic composition**, not as a permissive switch in the historical verifier.

## Actual synthetic transactions

`scripts/lib/syntheticWbsTransaction.ts` mints a new `dmk-wbs-synthetic-*` directory directly under the native canonical temporary directory. Before callbacks, ACL provisioning, marker creation or database opening, it pins the lexical root and exact parent/root BigInt device/inode identities as decimal strings, avoiding Number precision loss. Linux uses 0700; Windows restricts only the generated directory's DACL to the current SID. It records an unpredictable fixture owner marker, checks canonical paths, hard links/symlinks (including dangling database links before native open), ownership and replacement, and never accepts an arbitrary database path. Replaced roots are neither adopted nor deleted during failure cleanup. Reopening requires the original generated fixture handle. Its token is a synthetic ownership capability, not a real identity or governance credential. The implementation supports Windows/Linux Node 22 x64 and the already pinned `better-sqlite3` package.

One SQLite database owns fixture WBS bytes, exact canonical consumed-receipt ledger, retained exact before/after snapshots for each synthetic operation, raw receipt/envelope bytes, acquisition proof, monotonic high-water marks, predecessor, idempotency and audit records. Initial state must be the independently pinned historical WBS snapshot and empty historical ledger. It is copied into the disposable database; the original repository file remains unchanged.

SQLite uses WAL, `synchronous=FULL`, foreign keys, trusted schema disabled, busy timeout 100 ms and `BEGIN IMMEDIATE`. Each commit verifies exact protected revision, WBS/ledger bytes and commit/tree predicates, updates state, inserts unique receipt/envelope/nonce/idempotency records, and verifies integrity before commit. It reacquires and verifies the same signed authority immediately before commit under the local write transaction. Any change or revocation rejects and rolls back. Idempotency only returns an existing exact request's recorded historical result; it does not authorize new application under revoked authority. Different bytes under the same operation ID reject.

The same SQLite commit contains all synthetic state and consumption. Actual process exits after BEGIN, state update, receipt insertion and before COMMIT recover the old state without consumption; exit after COMMIT recovers the complete new state without a second consumption. `quick_check`, schema version, pinned genesis, retained snapshot continuity, raw artifact digests, canonical ledger, consumption counts and audit chain are verified on reads/restart. Tampering fails closed. No automatic reset, genesis recreation, history deletion or inferred successful retry repairs corrupt evidence.

**Restart/snapshot is local hash consistency, not fresh cryptographic or external attestation.** The original receipt/envelope/acquisition signatures are verified before the synthetic commit and retained, but `snapshot()` does not reverify every past signature or fetch current revocation/time/provenance. It has no independent rollback witness. A same-account adversary that rewrites the complete database, audit hashes and consistent receipts can evade local consistency checks; an entire older coherent database can also roll back. Independently authenticated current state, historical as-of trust/revocation adjudication and externally anchored monotonic checkpoints remain production blockers. This candidate does not claim complete historical receipt attestation.

**This is not an atomic transaction with a GitHub protected ref.** The synthetic ceremony precreates actual Git objects, witnesses their identities, then commits their fixture acknowledgment in SQLite. Production requires a separately administered broker and exact-base remote compare-and-swap/freshness protocol. A successful GitHub PR merge endpoint cannot atomically consume this SQLite receipt ledger or establish signing authority. A distributed failure or policy change after the final acquisition but before an external ref update remains outside this candidate; there is no operational writer to exploit that gap.

## Applied versus current Git state

`scripts/lib/syntheticWbsGit.ts` reads only generated `dmk-wbs-git-*` repositories with a TESTONLY marker. It disallows shallow histories, grafts, alternates, replacement objects and symlinked Git directories. Commands have time/output bounds. Raw Git commit/tree/blob hashes are independently recomputed; the fixed fixture root entries `wbs.yaml` and `ledger.json` must be regular 100644 blobs, and exact SHA-256 WBS/ledger bytes must remain unchanged in every descendant. Inert descriptor admission rejects accessors before execution. Production canonical-path acquisition is not implemented. Current-state verification has no caller-selected historical fallback.

The applied commit/tree remains pinned. A later current commit can pass only through a complete ordered first-parent chain of unchanged governed bytes and exact parent/object identities. Changed WBS or ledger, missing/reordered/duplicated ancestors, malformed objects, altered bytes, unknown sources or oversized chains reject. This is **first-parent-only compatibility**: paths where applied state is reachable exclusively through a merge's second parent reject. The fixture provider does not authenticate production protected refs, branch rules, GitHub repository identity or revocation/time services. Supplied consistent synthetic sources never establish operational authority.

## Candidate resource and compatibility constraints

These constraints require independent review; they are not ratified production capacity:

- Existing 2 MiB receipt/ledger/snapshot and offline-envelope JSON budgets, depth 64, 256-link bound and clock/checkpoint/uncertainty rules are retained. Derived canonical acquisition evidence can reach its existing 2 MiB JSON bound before each individual input reaches its cap; rejection is explicit, with no truncation.
- The new synthetic store limits successful applications to 256. It uses SQLite `max_page_count=16384` at the default 4096-byte page size (64 MiB database pages); WAL/SHM, allocator, raw acquisition, concurrent processes and total process-tree RSS are additional resources. This is a synthetic storage rejection boundary, not a process-memory promise or a disk-full qualification.
- Git proof admission permits at most 256 nodes and 64 MiB encoded proof bytes, including repeated governed blobs. Each commit is at most 128 KiB; each tree/WBS/ledger is at most 2 MiB. SHA-1 here verifies the repository's existing Git object identities; SHA-256 binds governed raw bytes. No stronger Git object-format claim is made.
- Timeout/fault tests prove behavior in disposable fixtures. Power loss, filesystem/device write-cache guarantees, disk-full recovery, malicious same-account processes, total process-tree capacity and remote authority concurrency remain unqualified. A hash chain without an external witness anchor cannot detect complete database rollback or coordinated history rewriting.
- Fixed eight-epoch measurements capture per-commit samples, p50/p95, process memory and CPU on the executing host. They exercise small synthetic proofs and do not establish worst-case admitted-proof capacity or operational budgets.
