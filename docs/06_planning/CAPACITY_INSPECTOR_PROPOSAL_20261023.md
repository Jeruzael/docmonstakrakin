## Proposed observation contract

Provide a separate offline local tool that emits bounded, nonsecret observations from an explicitly selected, stopped, private, provenance-valid authority image. **No inspector command exists yet.** No HTTP endpoint, live worker command, background polling, repair path or automatic fallback is proposed. This tool cannot grant access, certify human consent, make a backup current, qualify production readiness or approve a pilot.

Prefer an **independently created immutable read-only snapshot** if genuine in-place immutability cannot be established. Snapshot creation, stopping/checkpointing a source, acquisition of exclusive custody, volume/snapshot provisioning and signing/anchoring its custody receipt are separate reviewed operations. They are never hidden inside inspection. Existing backup creation is also a separate operation with its documented writes; calling it from the inspector is forbidden.

The inspector must refuse the source **before SQL** when admission cannot establish all of the following:

1. The exact local filesystem/platform/read-only profile is qualified; input is an existing regular single-link file beneath canonical, private, current-owner directories. Reject symlinks, junctions/reparse points, hardlinks, alternate stream/short-name/case/UNC/device/relative aliases, network/shared storage and unsupported file types. Never repair ownership/ACLs or create directories in the source tree.
2. There is trustworthy evidence of a stopped source and exclusive custody throughout measurement. Absence of `owner.lock`, process probing, an old PID or an operator assertion by itself does not exclude a competing writer. Any live, stale, malformed, unexpected or uncertain owner marker is a refusal; do not acquire, touch, remove or replace it. Do not weaken the authority's lock protocol to accommodate inspection.
3. The entire selected image is already complete and self-contained: refuse **any** WAL, SHM, rollback/hot journal, master/super-journal or unknown sidecar, including empty WAL/SHM. Do not ignore, copy around, checkpoint, truncate, delete, replay or regenerate these files. Refuse an image with unknown checkpoint/completeness history. A standalone database file copied while a source WAL existed may omit acknowledged commits; its hash cannot establish completeness.
4. Literal `WORKSPACE_AUTHORITY/1` provenance and the selected original source identities are known and admitted. For in-place input compare stored workspace/private `dev:ino` identities to independently measured original identities. For a detached snapshot, require a separately authenticated custody manifest binding the original identities/provenance, original DB hash, closed-state/completeness evidence, selected snapshot bytes, source revision, acquisition time and trusted current authority anchor. Snapshot filesystem identities legitimately differ; do not rewrite the database or compare them as though they were the original. Unknown/foreign/merely self-asserted provenance is BLOCKED.
5. Source immutability persists from the first inventory through final metadata verification. Use a qualified read-only immutable volume/snapshot or an equivalently proven OS/VFS handle contract that forbids competing writes, replacements and source namespace changes. An ordinary writable directory with repeated path/hash checks is insufficient against races. Never change a source ACL or mount setting to manufacture this condition inside the tool.
6. The tool and independent observer can read without changing source access times or other metadata. Strict non-mutation includes metadata, ACL/owner, link identities/counts, timestamps and directory entries. Account for lazy atime updates on Windows/Linux and the observer's own reads. A qualified read-only mount/snapshot/no-atime handle approach must be tested, not assumed. Do not restore timestamps afterward to conceal a write. If the platform cannot meet this contract, return BLOCKED with no capacity verdict.

Hash equality is useful change detection, **not proof that no writes occurred**, that no write-and-restore race happened, that a snapshot includes WAL commits, or that provenance/current revocation is authentic. Unprivileged filesystem checks cannot defend against arbitrary code running as the same OS owner or a privileged adversary; if that threat is present, the current local design is unsupported. A snapshot's self-contained manifest or a synthetic test signer supplies no production authority.

## SQLite mechanism to prove before implementation approval

SQLite's [URI contract](https://www.sqlite.org/uri.html) requires explicit URI recognition to apply `mode=ro&immutable=1`. Immutable mode opens read-only and omits SQLite locking/change detection; it is safe only when the input really cannot change. [SQLite's WAL documentation](https://www.sqlite.org/wal.html#read_only_databases) describes the extra conditions needed for read-only WAL access. These mechanisms do not prove stopped custody, provenance or filesystem metadata preservation.

The implementation candidate must demonstrate, on its pinned genuine native library, actual `SQLITE_OPEN_READONLY` and URI recognition (`SQLITE_OPEN_URI` or a verified equivalent), correct percent-encoding of a fixed admitted file URI, and effective `immutable=1` against a genuinely immutable source. Do not use `nolock=1` on mutable input. Deny SQL writes, ATTACH, extension loading, writable pragmas, journal transitions, checkpoints and user-selected SQL/VFS/module paths. No `WorkspaceStore.open`, worker startup, lock helper or authority initialization may be imported transitively. Use bounded trusted-schema-off validation and only fixed read queries.

The repository uses better-sqlite3 `13.0.3` / SQLite `3.53.4`. Its [documented constructor](https://github.com/WiseLibs/better-sqlite3/blob/v13.0.3/docs/api.md#new-databasepath-options) exposes `readonly`; that option alone does not establish immutable URI behavior or a no-sidecar/metadata guarantee. This proposal does **not** assert that passing a `file:` string to the current binding enables URI handling. Inspect/prove the actual native open flags and VFS behavior before selecting an API. If the existing pinned binding cannot meet the contract, keep the tool **BLOCKED** and review any driver/VFS/native dependency change as a new explicit implementation scope. Do not smuggle a dependency update or OS repair into this documentation approval.

There is a design choice still to ratify: a read-only filesystem image plus the pinned binding, or a separately reviewed native/VFS adapter with handle pinning and read-only/no-atime guarantees. Both need independent filesystem evidence. Ordinary `readonly: true`, `query_only`, a read transaction, a backup API call or copying only the main database does not satisfy this proposal by itself.

## Bounded validation and output

After admission, validate exact schema/user_version/native provenance, integrity/foreign keys, 4,096-count bounds, metadata integer/size bounds, complete hash chain/contiguous sequence and literal provenance without using the worker's startup routine (its full-capacity admission intentionally rejects). A valid fully retained authority is an inspectable **FULL observation**, not corruption and not permission to open it. More than 4,096 or invalid history is a refusal. Reuse reviewed pure validation logic only if it cannot invoke mutations; sharing/refactoring runtime code requires a separately reviewed patch.

Proposed result fields: proposal/schema/tool version and exact source revision; admitted input/custody-manifest/anchor hashes; immutable profile and observer receipt hashes; measured DB byte count; generation, policy/snapshot revisions and clock high-water; audit count/last sequence/head hash; `operations` and `used_digests` counts and remaining entries; active/revoked session aggregate counts; immutable local observation result (`VALID_BOUNDED`, `FULL`, `BLOCKED` or `INVALID`); reasons; `sourceMutated:false` only if independently evidenced; `activated:false`, `freshnessEstablished:false`, `pilotAuthorized:false`. These are **proposed output labels**, not existing runtime error codes.

Redact usernames/person IDs, verifiers, session/CSRF tokens, raw digests/operation IDs, project state, audit targets, full private paths and SQL exceptions. Counts/head hashes/identity hashes still belong in approved private custody. Write a bounded report only to an explicitly selected new external evidence directory or caller-owned output stream; never create source sidecars or append an audit event to record the inspection. No output should be published before full validation/final invariance checks succeed. On uncertainty emit only a bounded failure reason and preserve input. Failure output must not be an apparent capacity clearance.

Headroom is an observation, not a promise about future work. The minimum of audit/operation/digest remaining entries may constrain a workflow differently. Successful opens always consume audit. Session insertion/rotation can trigger `EXPIRED_SESSIONS_RECLAIMED` before its own event when the session table is full; an action can require more than one event and roll back if it cannot finish. Do not label an audit-only count as a safe action budget or recommend opening at 4,095 to measure it.

## Independent acceptance tests required for a future patch

Use only disposable synthetic authorities and independently prepared admitted immutable snapshots. The observer must be a separate harness/process outside the inspector, not a self-reported boolean. It must capture before/after complete source-directory entry sets, exact byte SHA-256/length for admitted files, native file identities/link counts, owner/ACL/attributes, high-resolution creation/write/access/change timestamps where supported, provenance bytes/hash and all metadata values. Qualify observer no-atime behavior too. Collect OS file-operation telemetry or an equivalently reviewed VFS assertion proving no write/create/delete/rename/lock/checkpoint path was attempted, including failure paths; identical end hashes alone are insufficient.

| Test family | Required observable acceptance |
| --- | --- |
| Audit 4,094 / 4,095 / 4,096 | Exact counts/headroom and FULL at 4,096, generation/revisions/clock/history unchanged; repeat inspection has the same source evidence. Never open through WorkspaceStore to inspect. Existing full-capacity rollback/diagnostic behavior remains separately tested. |
| Independent operation/digest ceilings | Report exact 4,094/4,095/4,096 counts independently; do not infer them from audit or live session count. Over-limit/schema-inconsistent fixture is refused. No identifiers leaked. |
| No-write success/failure | Independent full before/after invariance and write-attempt telemetry pass on Windows and Linux; no lock/WAL/SHM/journal or temporary source file appears, even after exceptions, close, cancellation or process kill. No atime repair. |
| Live / uncertain / stale owner | Refuse before database access without marker change, busy-wait, PID-based lock theft or recovery. Concurrent source start/writer invalidates admission; no result is published. |
| WAL/SHM and incompleteness | Refuse empty/nonempty/hot/committed-crash WAL, SHM, hot rollback journal and unknown extras. Prove a main-file-only copy with omitted committed WAL cannot receive VALID_BOUNDED. No automatic snapshot/backup/checkpoint fallback. |
| Path/permission races | Refuse hardlink/junction/reparse/alias/foreign owner/loose ACL, inode replacement, rename, ACL pin changes and path swaps at every boundary. Mutation between two equal snapshots must be caught by no-write/immutability evidence, not accepted by hash equality. |
| Corruption / provenance / rollback | Refuse unsupported schema/native version, damaged chain, missing/tampered tail, foreign literal provenance, self-signed unknown custody, stale independent anchor, missing receipt and incomplete snapshot lineage. Never rewrite provenance. |
| Driver/VFS proof | URI parameters shown effective, opened exact admitted file handle/image, no file creation on nonexistent/URI-confusion input, read-only media error paths preserved; no unsafe option/extension/user SQL. If not provable, supported result is BLOCKED. |
| Resource / privacy | Bounded DB/snapshot/rows/memory/time/open handles/output on Windows/Linux, disk-full external report and cancellation fail closed without source changes or private values in logs. No bulk live service. |

For physical size/read-resource planning use the existing backup format's 256 MiB DB/64 MiB snapshot ceilings as constraints to review, not a claim that the new tool's worst-case memory/latency is measured. This strict proposal refuses WAL rather than admitting the backup's 512 MiB WAL case. Accepting a new limit/profile requires an explicit design change and tests.
