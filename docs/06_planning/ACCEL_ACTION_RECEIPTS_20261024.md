## Exact receipt

Stored in same SQLite transaction as snapshot/operation/audit: version1, operationId, principalId, action, original requested project (or null), actual affected project, requestHash, effectHash, committed snapshotRevision and policyRevision. Canonical fixed-field JSON and its hash are validated against the operation row and original snapshot-commit audit revision; no full response bodies, credentials or session tokens. Existing limits bound operation count and receipt bytes. Missing historical bindings never become fabricated receipts.

`lookupReceipt` checks current valid session, matching stable actor, action/requested scope/body hash and current permissions including read access to the created target. Exact retry may refer to an earlier committed revision after later work; acknowledgment never certifies today's snapshot. Unknown operation is null only for a normal new request, never permission for automatic retry after an uncertain outcome. Any mismatch/legacy tombstone rejects. Full audit capacity continues to reject normal lookup; this slice is not capacity recovery.
