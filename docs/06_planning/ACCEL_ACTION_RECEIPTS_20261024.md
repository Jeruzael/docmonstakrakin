## Exact receipt

Stored in same SQLite transaction as snapshot/operation/audit: version1, operationId, principalId, action, original requested project (or null), actual affected project, requestHash, effectHash, committed snapshotRevision and policyRevision. Canonical fixed-field JSON and its hash are validated against the operation row, original snapshot-commit audit revision and a second `ACTION_RECEIPT_COMMITTED` hash commitment using the unchanged audit event format. Two audit rows per new receipt operation; zero additional rows on exact lookup/replay; the4096 ceiling is unchanged and insufficient capacity rolls back both events and the entire mutation. No full response bodies, credentials or session tokens. Existing limits bound operation count and receipt bytes. Missing historical bindings never become fabricated receipts.

`lookupReceipt` checks current valid session, matching stable actor, action/requested scope/body hash and current permissions including read access to the created target. Exact retry may refer to an earlier committed revision after later work; acknowledgment never certifies today's snapshot. Unknown operation is null only for a normal new request, never permission for automatic retry after an uncertain outcome. Any mismatch/legacy tombstone rejects. Full audit capacity continues to reject normal lookup; this slice is not capacity recovery.

Protocol1 explicitly rejects `POST /api/projects/package/import`: its current authorization changes from `project:create` to `project:import` once a new target exists. Reinterpreting that stored action would weaken exact intent binding. The legacy importer remains available with its existing replay rejection; stable import action semantics are a remaining package12 compatibility requirement. A workspace capability header does not claim every route implements the opt-in protocol.
