## Problem and existing evidence

At runtime `62d66779b9d7236e093eb2fd8e47355c8d42b798`, [worker.cjs](../../server/security/workspaceAccess/worker.cjs) independently bounds audit, operation IDs and used session digests at 4,096 records. `transaction()` checks audit capacity even for authenticated access. `event()` guards each append; failed transactions roll back snapshot/ownership/clock/history changes. Startup validates the retained authority and refuses audit count 4,096 before write admission. Every successful open increments generation and appends `AUTHORITY_OPENED`; offline `status` also opens. An open at 4,095 can consume the last event.

Thus normal authenticated reads, login, rotation and logout can fail closed at full capacity. [HTTP/service source](../../server/security/workspaceAccess/http.ts) maps login unavailability to 503 `AUTHORITY_UNAVAILABLE` and failed logout to 403 `CSRF_OR_SESSION_INVALID`; a failed logout is not successful revocation. Existing-worker `info`/`snapshot`/`audit` diagnostics remain readable without ordinary transactions; they grant no normal HTTP read bypass. WS12 in [testWorkspaceStore.ts](../../scripts/testWorkspaceStore.ts) proves synthetic full-capacity rollback and diagnostic reads after an open/issue sequence from 4,094. It is not a durability/cutover test and never qualifies an original precious authority for exhaustion.

[ADR-0004](../05_decisions/ADR/ADR-0004-cryptographic-hash-chained-audit-ledger.md) establishes append-only hash chaining. The exact authority implementation serializes its own raw fields and computes `SHA256(previousHash + '\n' + raw)`; preserve those literal historical bytes rather than reserializing them to the ADR's conceptual notation. [DMK-120's canonical scope](../00_control/MASTER_WBS.yaml) covers hash linkage/tamper detection, not a new retention or successor policy. Hashes without an independently retained trusted head do not establish current custody, prevent tail truncation/rollback or appoint an authorized signer.

Existing [backup/restore preparation](../07_verification/WORKSPACE_BACKUP_RECOVERY_20261022.md) preserves a consistent committed copy under explicit exclusive coordination, and unactivated preparation retains original provenance. A foreign prepared copy must fail `WORKSPACE_PATH_INVALID`; backup self-manifests do not establish current revocation, time or antirollback authority. Restart, lock recovery, backup, a new database and a restored-copy pathname are not continuity remedies.

## Policy decision proposed for review

Develop an **anchored append-only segment lineage with an explicit successor authority**, preserving old segments as immutable retained history. This is a proposed direction, not an accepted policy. Alternatives and exact format/threshold/custody values need human ratification before a coding slice. The current runtime remains unchanged and fails closed at its existing ceilings.

Each sealed segment retains all original audit rows/raw bytes/sequence/hash linkage, operation IDs and used digests (plus the state necessary to interpret them). A successor's genesis binds the predecessor's independently anchored terminal state and exact retained segment inventory. A globally ordered lineage and an independently current authority pointer establish which writer may act; the predecessor cannot silently resume after cutover. Do not reset a chain to an unanchored genesis, empty replay tables or a fresh generation that forgets history.

The remedy must address all three histories. Moving only audit rows leaves operation/digest ceilings; dropping them allows old operation or token replay. Expired/revoked session reclamation is not deletion permission for used digests or committed operation IDs. No audit deletion, retention reduction, compaction that loses logical records, ceiling increase, guard bypass, automatic recovery activation or bulk operator experiment is proposed.

## Required invariants and durable records

These are proposed acceptance requirements. Names such as “seal,” “genesis” and “authority pointer” describe design records; no new schema or existing runtime command is claimed.

1. **Complete history:** preserve every predecessor audit row exactly, including raw bytes, previous/head hashes, sequence, generation/policy/snapshot observations and literal original provenance. Define global ordering as immutable `(lineageId, segmentOrdinal, localSequence)` or another reviewed unambiguous order; never relabel historical local sequences or hide an old segment. A successor genesis references the predecessor terminal audit head/count and signed/approved segment inventory. Verify every link back to the accepted original anchor.
2. **Replay continuity:** retain every operation ID and used digest across all sealed and current segments. Before accepting an operation, consult the complete admitted lineage's replay index; same ID with the same or changed body must not cause a second commit. Preserve the current reject-on-replay behavior unless a separately ratified idempotent-response contract changes it. A rebuildable authenticated index may accelerate lookup, but no Bloom filter/partial cache is the sole decision authority; a missing/corrupt/stale index is unavailable, not “not seen.” Record operation-to-snapshot semantics and any future canonical request digest atomically. Do not fabricate body hashes for historical operations whose schema stored only ID/revision.
3. **State and authority binding:** seal binds exact DB/segment/snapshot hashes, schema/native/version/profile, complete replay inventory roots/counts, predecessor provenance/authority ID and generation/policy/snapshot/clock high-water, predecessor head, successor identity/path and new schema identity. An immutable manifest must enumerate all required segments; latest manifest plus data alone is not current authority. Link the approved decision/custodian and independent anchor receipt without private credentials.
4. **Independent custody/currentness:** retain segment bytes and manifests privately in explicitly appointed custody with tested restore/read verification and independent current-head anchors. Specify the real custodian, signer/verification keys, key scope/rotation/revocation, quorum and allowed media/service before implementation. A self-signed artifact, Git hash/account attribution, agent approval or synthetic signer is not production trust/independent-human authority. Unknown/missing/unavailable/stale anchor or signer is BLOCKED, even if the local chain verifies.
5. **Generation/CAS and single writer:** transition compares exact predecessor authority ID, generation, policy/snapshot revisions, clock/head/counts, provenance and current independent pointer (including pointer revision). Mismatch invalidates the plan without replaying it automatically. Publish an authoritative monotonic epoch/pointer so both normal startup and all writers reject the retired predecessor and unactivated staged successor. A renamed directory alone is insufficient. Require exactly one admitted active authority or a closed unavailable state; never two independent writers.
6. **Session/revocation fence:** no predecessor or copied session becomes active on a successor. Revoke/fence all old sessions using authority ID plus strictly advancing generation/epoch and fresh service keys before accepting requests; preserve used-digest history. Retain disabled principals, credential revisions, memberships/DENY, policy revision and known revocations exactly. Establish current revocation from the authoritative anchor, not only the older snapshot. Unacknowledged logout remains unacknowledged; cutover cannot retroactively call it a success.
7. **Clock/antirollback:** successor clock high-water cannot be below any admitted predecessor/current revocation/anchor high-water. Specify tolerated clock source/skew and future-clock behavior; backward/uncertain time fails closed. Prevent restored old source/successor, old manifests or pointer/anchor rollback from becoming current. Independent monotonic state is required; a mutable same-disk counter or solely hash-valid backup is insufficient. When that state is unreachable, block rather than reconstruct trust from local bytes.
8. **Crash and acknowledgement:** distinguish staged data, flushed sealed data, prepared successor, committed authority pointer and served acknowledgement. Preserve the predecessor bytes and pending decision after every failure. Acknowledgement means the reviewed durable commitment is established, including required data/manifest/pointer/anchor flush order. File flush plus rename must be tested on each supported platform/filesystem; do not infer power-loss durability from successful process-kill tests. No acknowledged operation disappears after crash; an uncertain result must be reconciled by exact operation ID under the current authority, never blindly replayed.
9. **Resources and retention:** choose per-segment record/byte limits and disk reserve/maximum admitted lineage counts, memory/query/open-handle/time budgets, verified replay indexing/rebuild strategy and custody availability policy. Keep logical history indefinitely until a separate retention policy is ratified; finite local/custody resources must cause early admission stop, not silent deletion or unlimited growth. Specify disk-full behavior before cutover, output publication and acknowledgement. Preserve bounded reads/transport; segmentation must not load all history into RAM or scan without deadline on every request.

Physical size constraints in the existing authority/backup format (256 MiB main database, 64 MiB snapshot; backup's 512 MiB input WAL) are existing limits, not measured budgets for this proposed lineage. New formats and resource choices require an explicit reviewed contract. No new numeric threshold or reserve is ratified in this document.

## Proposed transition model and failure handling

Reserve a reviewed finite headroom budget **before** exhaustion. Budget every store/status/CLI/server open and every audited operation, including possible session reclamation plus issuance/rotation and the protocol's own cutover events. Record exact preconditions and worst-case counts; do not use a status-open to discover whether the last slot exists. Inspector output is only a point-in-time observation and must meet its separate no-write contract. No live status polling or unbounded “retry until green.”

There is no transaction atomic across an arbitrary independent custody/anchor service and a local filesystem by assumption. The implementation must specify a recoverable state machine with idempotent signed/authorized intent/prepare/commit receipts, exact compare-and-swap revisions, ordering and reconciliation for partial delivery. If that protocol cannot establish a single durable current authority, phase 4 remains BLOCKED. Do not call a pair of successful renames distributed atomicity.

**At 4,096:** current startup cannot open the predecessor to append a seal. Do not disable that check or require an impossible “last event” in the existing full database. A separately ratified offline custody/transition protocol may anchor the complete stopped immutable predecessor externally and create a successor genesis that records the transition, without editing predecessor history. Its full-capacity authorization/revocation/currentness/antirollback basis is a decision still required; it is not implemented or authorized by this proposal. Unknown custody, WAL completeness or latest pointer makes this path BLOCKED. Near-full transition and full recovery are different operational approvals.

**Rollback:** before committed cutover, keep the old authority unavailable until the protocol proves it still owns the current pointer and any staged/anchored transition is safely cancelled by authorized durable receipt. After cutover, do not reactivate the predecessor or restore an older pointer. A defect requires a separately authorized forward successor/recovery preserving the lineage and revocation fence. Retain incomplete/retired artifacts; no recursive cleanup or retention deletion is granted.
