## Exact implementation boundary

The ordinary `createAuthPilot()` and synthetic-foundations factories still create fresh owned schema1 stores. Their default is inactive and no environment variable mounts authentication. The separate `createRecoveryAuthPilot()` is also inactive by default. Its explicit disconnected synthetic mode shares the same real authentication service, Argon2id verifier, digest-only sessions, CSRF, policy and audit logic. It can mint a TESTONLY schema2 store or acquire one using a canonical signed transfer and an independently supplied ephemeral test root. It accepts no caller-selected directory, database, connection or operational trust adapter. Neither factory is imported by the normal product server.

Schema2 is an opt-in test storage profile, not a migration of schema1. Unknown versions, cross-profile opening and downgrade are rejected. No existing schema1 database is upgraded. A schema2 lease pins the test public-root digest, a random 256-bit process-owner capability, ACTIVE/QUIESCED phase, pending transfer digest and deadline. A bounded consumed-transfer ledger records sequence, nonce digest, from/to generations and consumption time. The existing deterministic audit chain binds every preparation and claim to the same nonce digest and time. Startup checks ledger order, positive adjacent generations, exact claim/audit correspondence, outstanding preparation and lease consistency. Deleting a consumed row or altering its digest while keeping the audit fails. This is local consistency checking; there is no independently anchored anti-rollback checkpoint.

The sender atomically quiesces its lease and records preparation before asking the fixture signer to seal the receipt. Its manager reserves nondeleting custody before dispatch, including when the actual COMMIT succeeds but its reply is lost. The envelope binds profile/domain, exact root/parent identities and canonical paths, the owner marker, pinned root digest, nonce, generation and the exact prepared time window. It uses canonical flat JSON, Ed25519 and domain-separated SHA-256. Duplicate or escaped keys, alternate serialization, malformed UTF-8, unsupported fields, bad signatures and key substitution fail before acquisition. A valid signature is intent only: an ACTIVE store, wrong pending nonce/generation/window, expired preparation or consumed receipt cannot be claimed.

The receiver checks the canonical current temp-parent domain, minted-root basename, native directory identities and exact owned marker before SQLite opens. Marker admission reads exactly 64 bytes through a descriptor and verifies regular-file type, single link, fixed size and pre/open/post native identity. Buffer equality is exact; ASCII high-bit folding is rejected. Existing ownership limitations still apply: this is not an OS broker or race-free isolation from a process controlling the same OS identity and code.

Claim, receipt consumption, new random owner, generation increment and audit are one immediate SQLite transaction with WAL and synchronous FULL. Audit failure rolls back all of them. Every schema2 RPC read or mutation checks the persisted owner inside its own immediate transaction. Old processes cannot read credentials, acquire sessions, mutate policy or use administration after quiescence or succession. Public `execute()` cannot bypass the reserved manager preparation protocol. Connection close is harmless, while filesystem cleanup requires the exact active-owner receipt; a stale, transferred or uncertain manager retains the directory. All generated-fixture cleanup in the tests occurs only after the relevant children stop and the pinned directory/marker are rechecked.

Schema2 explicitly rejects the diagnostic `checkpoint` RPC: SQLite cannot run that pragma inside the owner transaction, and no racy check-then-checkpoint exception is added. Normal schema1 checkpoint behavior is preserved. The schema2 service can recreate server-owned handles for already configured synthetic resource IDs through one fixed `resourceExists` read; a caller-provided object still cannot become a policy handle. HTTP receives neither storage commands nor fixture administration.
