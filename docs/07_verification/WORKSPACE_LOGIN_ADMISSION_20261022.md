# Workspace public login admission and retained audit

This candidate distinguishes bounded mutable rate counters from authoritative append-only security history. It changes no principal, membership, role, password profile, session lifetime, snapshot scope, authority schema, or capacity limit. All examples and verification state are disposable synthetic fixtures; no operator identity or workspace is initialized.

The HTTP login path is public so an unauthenticated loopback process can reach its rate limiter. Recording a new critical audit event for every admitted attempt, throttled retry, and expired rate window lets that process consume the entire 4096-event lifetime history budget without credentials. The global limit of 30 attempts per minute did not bound that audit growth.

The counter table retains the existing five attempts per account and 30 global attempts per 60-second window. Its rows persist across restart and remain bounded to 128 keys. The worker checks the global counter before allocating a new account key, so attempts already denied globally cannot exhaust the table by varying account names. Counters saturate; expired rate windows may be reclaimed. These are rate-control observations, not authenticated evidence or an append-only record of every public request.

Public login admission and rate-window reclamation append no new retained authority audit records. They never remove or rewrite an existing record. Successful session issuance/rotation/revocation, principal and membership changes, project commits, and authority opening retain their existing audit events. A full critical audit still rejects login admission before any counter or clock change; it cannot falsely return success or authorize a session.

This closes unauthenticated per-request growth of the critical history; it does not provide unlimited authority storage. Successful activity can still fill the 4096-event retained budget. That fail-closed boundary requires deliberate stopped-state preservation and a separately accepted continuation/recovery policy. No silent history pruning, capacity increase, authority rebind, or backup activation follows from this change.

`scripts/testWorkspaceLoginAdmission.ts` covers repeated per-name denials, randomized globally denied names, exact audit preservation and chain consistency, rate-window reclamation, restart persistence, retained successful security events, and full-audit rollback. The genuine SQLite worker regression first produced one pass and two failures: globally denied names allocated additional keys, and public attempts grew retained history. After the change all three cases passed on Windows x64 with portable Node 22.23.3 and the pinned better-sqlite3 13.0.3 / SQLite 3.53.4 runtime. This focused run used the existing retained dependency tree; it is not a new installation qualification or a production capacity ratification.
