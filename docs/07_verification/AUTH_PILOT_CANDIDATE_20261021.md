# Disconnected S2-A authentication pilot candidate — 2026-10-21

Baseline: `148be8892b37aaf1944aca0c0671b6a948192f38`. Authority is Workstream B of the operator's Autonomous Completion Campaign. This is reusable authentication code and actual-server synthetic verification. It does not enable product authentication, enroll an operator, grant product permissions or complete DMK-209–214.

## Implemented boundary

`createAuthPilot()` is inert by default even with ambient enable variables. Explicit code must select `enabled: true, mode: 'DISCONNECTED_SYNTHETIC'`; the factory cannot select an existing database, operator directory or authority adapter. It creates only an owned disposable private store. Synthetic fixture IDs must begin `fixture-`. Normal `server.ts` and `src/App.tsx` do not import this family. No normal startup flag mounts these routes.

The implementation reuses the integrated, version-pinned asynchronous Argon2id verifier, sole SQLite worker, private-directory ownership checks, digest-only sessions, default-deny policy and deterministic audit chain. Native versions remain `argon2 0.45.1`, `better-sqlite3 13.0.3`, SQLite `3.53.4`. Package declarations and both lockfiles are unchanged.

The owned schema remains version 1 with WAL, synchronous FULL, foreign keys, bounded worker requests and immediate transactions. Worker restart checks schema/integrity/audits and increments a persisted generation before reopening authority. Existing sessions then fail. Unknown schema versions fail without migration or downgrade. This demonstrates worker recovery in a retained test-owned store; cross-process durable acquisition, backups and production schema migrations remain absent.

Candidate enrollment/change inputs require at least 12 UTF-16 code units and at most 1,024 UTF-8 bytes; login accepts nonempty exact UTF-8 within the same maximum. This is bounded synthetic input admission, not an entropy assessment or approved human password policy. No public registration or password-recovery endpoint exists.

HUMAN credentials support creation, bounded verification, session-bound current-password change, offline synthetic reset and disable. AGENT records cannot password-login or satisfy human-only policy. Credential changes compare the active session, generation, policy and exact credential revision inside the same transaction that replaces the verifier and writes the audit. Every prior session is invalidated by the new credential revision. Audit failure rolls back both credential and session creation; a token is exposed only after the session-and-audit transaction succeeds. The two new fixed worker commands accept only validated primitive fields; no raw SQL or request-selected command reaches HTTP.

The candidate accepts no password normalization or weaker KDF fallback. Direct fixture and service inputs also reject unpaired UTF-16 before native UTF-8 conversion: an executable missing-rejection RED case preceded that correction, and the final focused GREEN log retains the same 39 compound check names. PHC parameters and canonical encoding are validated before native work. KDF admission remains two active/four queued native operations per verifier, with the original queue timeout. Authentication additionally admits five attempts per principal and thirty globally per sixty-second window, at most 128 hashed throttle keys. Valid and unknown identities consume the same budgets. These are proposed development constraints, not ratified production password or abuse-control policy. Throttle state survives worker restart but is process-local and resets on full process replacement. Multi-process throttling and capacity are unqualified.

Opaque tokens remain 32 random bytes and only SHA-256 digests enter SQLite or worker messages. Rotation atomically consumes the old session and retains original absolute expiration. Logout, reset, disable, policy change, restart generation, idle/absolute expiration and backwards time fence acceptance. CSRF proofs are domain-separated, process-secret HMACs bound to the raw token, compared in constant time. Neither token nor password/verifier appears in JSON responses or audits. An HTTP cookie necessarily carries the raw bearer token to its browser; it is Secure, HttpOnly, host-only, SameSite=Strict, Path=/ and has the `__Host-` prefix.

Resource handles are object capabilities held in a per-service WeakMap. Plain IDs, forged handles, unknown actions and capabilities from another instance do not acquire authority. The router never takes an action, grant, role or resource handle from JSON. Internal test grants use the existing synthetic action registry; they do not map HUMAN_APPROVE to an operational Security Officer/Lead Architect quorum or GitHub reviewer identity.

## Actual HTTP pilot

`startDisconnectedAuthPilot()` starts nothing by default. An explicit synthetic caller supplies its own temporary TLS key/certificate and receives a dedicated ephemeral-port server bound only to `127.0.0.1`. This does not install or trust certificates. The test client verifies the generated self-signed certificate's IP identity using its private per-test CA parameter; it never disables certificate verification. Production TLS provisioning, trust, custody and rotation remain human decisions.

Cookies do not isolate TCP ports. The numeric loopback test host is not a ratified production cookie hostname: another trusted HTTPS receiver for the same host/path could receive its cookie. Production hostname/certificate ownership and other local services must be reviewed before browser activation; exact Origin checks do not prevent bearer exfiltration to a different trusted receiver. This family provides no same-user process isolation.

The six dedicated registrations are POST `/pilot/auth/login`, GET and POST `/pilot/auth/session`, POST `/pilot/auth/rotate`, POST `/pilot/auth/logout` and POST `/pilot/auth/password`. No enrollment, recovery, grant, project, agent or privileged route is mounted. Login requires exact same Origin, Host and custom pilot header; state-changing authenticated operations also require the token-bound CSRF proof. Duplicate security headers, cross-site fetch metadata, forwarded authority headers and query strings fail. Flat UTF-8 JSON rejects duplicates, escaped duplicate keys, prototype fields, nested values, invalid Unicode, extra/missing keys and trailing data. JSON bodies and TLS headers each have an 8 KiB admission ceiling, with 32 headers, 16 connections and five-second TLS handshake/request/header/socket timeouts. Responses are no-store and expose no CORS authority. These development admission values also need operational review.

Browsers may omit Origin on same-origin GET, so the POST self-inspection path provides a usable browser-generated Origin without relaxing the mandatory check. Strict GET remains available to clients that actually send Origin. A genuine POST/HTTP missing-route RED case preceded the addition. Real Chrome 155.0.8059.79 then exercised automatic Origin, login, Secure/HttpOnly/Strict cookie storage, POST self-inspection, strict-GET rejection, CSRF rejection, cross-origin denial without authority mutation, and logout/cookie removal. Only empty fixture documents are fulfilled by Playwright; every authentication request reaches the actual HTTPS Express server. The browser uses a per-process exception for the generated certificate's exact SPKI hash, with `ignoreHTTPSErrors: false`, no blanket certificate-error switch and no host certificate installation. This is a synthetic browser contract qualification, not production CA/hostname trust. Node HTTPS separately validates the actual certificate chain and IP SAN. The scope of Chromium's exception is visible in its [certificate verifier implementation](https://chromium.googlesource.com/chromium/src/+/main/services/network/ignore_errors_cert_verifier.cc).

## Acceptance and verification

Run from an ordinary checkout with a physical fresh dependency installation, or an explicitly recorded retained test fixture:

```text
node --import tsx scripts/testAuthPilot.ts
npm run ci:quality
npm run ci:controlled-docs
npm run ci:regression
npm audit --json
```

Node 22 x64 and the existing native-toolchain qualifications apply. The test generates an ephemeral certificate with `openssl` (Linux) or the existing Git for Windows OpenSSL. It removes both test TLS material and its owned identity store. No private key is committed. The native packages are development dependencies because this family is disconnected; production packaging and authority-store acquisition remain future work.

The final focused suite has 41 named checks. It tests actual native KDF/SQLite operations, actual Express HTTPS requests and the real browser contract. Positive/negative evidence includes unknown/AGENT/forged identities; strict inputs/hostile PHC; per-principal/global/concurrent admission; atomic rotation; current-password change and competing revision changes; reset/disable; worker crash recovery; unsupported schema; audit-trigger failure rollback; default-deny handles and explicit denial; inclusive expiry/backwards time; cookies, Origin/Host/proxy/header/CSRF/body attacks; no product mounts; and private cleanup. The full runner counts named outputs; compound checks include multiple assertions. A full 72-suite / 1,943-check pass, quality/build and controlled 40/29/11 pass are retained from the preceding 39-check version. They are not relabeled as full-regression proof for the later POST/browser extension. Final exact-HEAD CI must supply that proof; final local focused 41/41 and TypeScript pass separately.

On Windows Node `22.21.1` x64, seven sequential real logins using a fixed 26-byte synthetic password, Argon2id 32 MiB/t=3/p=1 and SQLite WAL/FULL measured p50 **159.83 ms**, p95 **178.92 ms**, range **136.30–178.92 ms**. The worker shares this process; total process-tree capacity, saturation, realistic enrollment sizes, durable storage failures and production workloads are not established. Other campaign work and regression ran concurrently, so these synthetic timings are measurements, not an acceptance budget or isolated hardware benchmark. A repeat after the strict UTF-8 guard measured p50 80.74 ms, p95 84.29 ms, range 79.15–84.29 ms, sampled peak RSS 128,069,632 bytes, lifetime maxRSS 166,200 KiB, event-loop p95/max 20.05/21.41 ms, CPU user/system 454,000/110,000 microseconds. Both logs are retained separately; their variability prevents an operational performance claim. Linux measurements must come from actual CI and cannot be inferred from Windows.

Local focused/quality/controlled checks use the separately retained physical package fixture through a new task-owned read-only-use junction. Fresh npm audit returned zero reported vulnerabilities with the unchanged lockfile. ## Cutover inventory and remaining work

The original product inventory remains **69 registrations**: **45 legacy local unscoped**, **14 blocked privileged**, **7 specialized reviewer**, **3 reviewer-session**. Focused checks assert all five counts. Ordinary project/status APIs remain unauthenticated under their existing partial-containment contract. Adding this dedicated login pilot protects none of those existing routes.

Before any route-family cutover, independently approve identity/bootstrap/recovery authority, operational private-store ownership and version migrations, durable external audit head/checkpoint custody, trusted time, enrollment, browser trust, password/session/abuse budgets, production dependency packaging, legacy/reviewer identity reconciliation, resource mapping and a coordinator that rechecks all revisions before protected domain commits. JSON/document persistence and SQLite are not one ACID transaction; ambiguous cross-store recovery must deny protected work. Test actual disk-full, read-only, process/power loss and attacker-controlled directory replacement under the separately reviewed Windows canonicalization candidate. Do not reinterpret trigger rollback or worker termination as proof of every physical durability failure.

The fixture API is deliberately synthetic and includes test-only reset, rule and fault controls. It is never an enrollment or recovery interface. A same-user compromised process can replace code, read its bearer material or tamper with an unanchored local audit tail; this candidate is not an OS isolation or external-trust boundary. Operational offline ceremonies, recovery custodians, real grants and human quorum remain unimplemented and unauthorized. Full-process restart loses its process-local throttle/CSRF secret and fences store sessions only when the owned kernel is reacquired; no production reacquisition adapter exists.
