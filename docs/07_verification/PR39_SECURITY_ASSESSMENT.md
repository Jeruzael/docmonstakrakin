## 1. Executive Summary

This independent security assessment evaluates GitHub PR #39, which introduces corrective hardening for the Stage B2b1 read-only WBS registration transaction preflight module ([`scripts/planWbsRegistrationTransaction.ts`](../../scripts/planWbsRegistrationTransaction.ts)) following the premature merge of PR #38.

The assessment investigated whether PR #39 successfully resolves the findings identified in the PR #38 security review without introducing new vulnerabilities, bypasses, or unauthorized mutation authority.

### High-Level Summary of Findings & Limitations
- **28 Defensive Checks (Post-B08 Remediation; 27 Pre-Fix):** Confirmed passing fail-closed across all schema, prototype, hashing, chain-continuity, and ledger WBS state-cycle vectors.
- **5 Initial Security Findings (A04, A05, A10, A11, B08) — 1 Remediated (B08), 4 Remaining Bounded Risks:**
  - **Finding B08 (`FIXED_AND_VERIFIED`):** Pre-fix `parseLedger()` checked only adjacent `preWbsSha256 === cursor && postWbsSha256 !== cursor`, allowing a multi-step cycle (`Genesis -> State X -> Genesis`) to pass ledger parsing and allowing a subsequent additive registration from `Genesis -> W1` to preview `VALID` (preserved in [`pr39_adversarial.log`](pr39_adversarial.log)). Remediated in `parseLedger()` by tracking `seenWbsStates` initialized with `HISTORICAL_WBS_SHA256` and rejecting any repeated WBS state hash fail-closed (`"Receipt ledger chain contains a WBS state cycle or repeated WBS digest"`), verified in [`pr39_adversarial.post_b08_fix.log`](pr39_adversarial.post_b08_fix.log) and `scripts/testPlanWbsRegistrationTransaction.ts` (26/26 checks).
  - **Findings A04, A05, A10, and A11 (`ACCEPTABLE_BOUNDED_RISK`):** In-memory JavaScript representation nuances that either fail closed on second-pass canonical re-validation (A04, A05) or have zero effect on canonical digest computation (A10, A11).
- **5 Known Production Limitations (A13, B07, B09, C07, D01 — Remain Open):** Analyzed and confirmed to represent authentic trust boundaries of a read-only planning preflight, remaining mandatory `DEFERRED_PRODUCTION_BLOCKER` items for Stage B2b2 / production execution.
- **Unconditional Read-Only Guarantee:** `mayApply: false` remains hardcoded, unconditional, and verified across all test runs.

### Finding 1: SEC-FINDING-A04 — Array Hole + Extra Named Property in Signatures Array

- **Finding ID:** `SEC-FINDING-A04`
- **Severity:** Low (Informational Defense-in-Depth Nuance)
- **Exact File & Lines:** [`scripts/planWbsRegistrationTransaction.ts#L278-L284`](../../scripts/planWbsRegistrationTransaction.ts#L278-L284)
- **Attack Conditions & Required Privileges:** Attacker passes an in-memory JavaScript `SignedReceiptV2` object directly into `previewWbsRegistrationTransaction`. An array is constructed with a sparse hole (`[sig0, , sig1]`) and an extra named string property (`arr.extra = 'x'`). Because `Object.keys(arr)` returns `['0', '2', 'extra']` (length 3) and `arr.length` is 3, the first-pass length guard `Object.keys(rawSignatures).length !== rawSignatures.length` evaluates to `3 !== 3` (`false`) and does not throw.
- **Does Attack Actually Succeed?** **NO (FAILS CLOSED)**.
  When `rawSignatures.map` runs, JavaScript's `map` skips the hole at index 1. The resulting array `normalizedSignatures` has length 3 with a hole at index 1, but does *not* inherit the `.extra` string property. When `normalizedSignatures.sort()` runs, the empty slot is moved to the end (`index 2`). Subsequently, line 519 calls `signedReceiptDigestV2(normalizedReceipt)`, which calls `canonicalSignedReceiptPayloadV2(normalizedReceipt)`, which calls `validateAndNormalizeSignedReceiptV2(normalizedReceipt)` a second time. On this second pass, `Object.keys(signatures)` has length 2 (`['0', '1']`), while `length` is 3 (`2 !== 3`), triggering immediate rejection: `"Signed receipt signatures must be a non-empty array"`. If passed directly to `verifyTrustedWbsRegistrationV2`, line 273 encounters `undefined` and fails (`!signature || signature.kind !== 'HUMAN'`). Under no circumstances is an unapproved item accepted or invalid signature bypassed.
- **Complete Reproducible Test Case:**
  ```typescript
  const sigs: any = [R1.signatures[0], , R1.signatures[1]];
  sigs.extra = 'x';
  assert.equal(sigs.length, 3);
  assert.equal(Object.keys(sigs).length, 3); // Bypasses first-pass length check
  const r = previewWbsRegistrationTransaction({ ...base, receipt: { intent: I1, signatures: sigs } });
  assert.equal(r.valid, false);
  assert.equal(r.mode, 'REJECTED');
  assert.ok(r.errors.some(e => e.includes('Signed receipt signatures must be a non-empty array')));
  ```
- **Expected vs Observed Result:**
  - *Expected:* Rejection of malformed array.
  - *Observed:* Rejected fail-closed by second-pass canonical re-validation.
- **Stage B2b1 vs Unimplemented Integration:** Exists strictly in JavaScript in-memory runtime objects. Over JSON serialization (wire/disk), array holes cannot exist (JSON renders `[a, null, b]` which has type `object`/`null` and fails line 289 `isPlainObject`), and non-index properties are stripped by `JSON.stringify`.
- **Recommended Remediation:** Strengthen array validation by checking for index holes directly:
  ```typescript
  for (let i = 0; i < rawSignatures.length; i++) {
    if (!(i in rawSignatures)) throw new Error('Signed receipt signatures contains array holes');
  }
  ```
- **Merge-Blocking Status:** `NOT_MERGE_BLOCKING` (Fails closed on both validation passes).
- **Classification:** `ACCEPTABLE_BOUNDED_RISK`.

### Finding 3: SEC-FINDING-A10 — Non-Enumerable Extra Properties on Intent/Receipt

- **Finding ID:** `SEC-FINDING-A10`
- **Severity:** Informational
- **Exact File & Lines:** [`scripts/planWbsRegistrationTransaction.ts#L138-L147`](../../scripts/planWbsRegistrationTransaction.ts#L138-L147), [`scripts/planWbsRegistrationTransaction.ts#L182-L245`](../../scripts/planWbsRegistrationTransaction.ts#L182-L245)
- **Attack Conditions & Required Privileges:** Attacker attaches a non-enumerable property to the intent or receipt object using `Object.defineProperty(intent, 'secret', { value: 'hidden', enumerable: false })`.
- **Does Attack Actually Succeed?** **NO EXPLOITABLE IMPACT**.
  `hasExactKeys` uses `Object.keys(obj)`, which inspects only enumerable properties. Non-enumerable properties are completely ignored. However, because `validateAndNormalizeSignedReceiptV2` deep-clones fields into a fresh plain object using explicit property assignment, the non-enumerable property is **not copied** to `normalizedReceipt`. The canonical payload and hash are computed strictly over `normalizedReceipt`. Thus, the non-enumerable property has zero influence on verification, hashing, or proposed ledger output.
- **Complete Reproducible Test Case:**
  ```typescript
  const intentWithHidden: any = { ...I1 };
  Object.defineProperty(intentWithHidden, 'hiddenPayload', { value: 'malicious', enumerable: false });
  const r = previewWbsRegistrationTransaction({ ...base, receipt: { intent: intentWithHidden, signatures: R1.signatures } });
  assert.equal(r.valid, true);
  assert.equal('hiddenPayload' in r.proposedLedgerSha256, false);
  ```
- **Expected vs Observed Result:**
  - *Expected:* Clean normalization ignoring non-enumerable properties.
  - *Observed:* Identical canonical hash; non-enumerable property completely dropped.
- **Stage B2b1 vs Unimplemented Integration:** Stage B2b1 in-memory behavior.
- **Recommended Remediation:** If strict rejection of non-enumerable properties is desired in memory, check `Object.getOwnPropertyNames(obj)`.
- **Merge-Blocking Status:** `NOT_MERGE_BLOCKING`.
- **Classification:** `ACCEPTABLE_BOUNDED_RISK`.

### Finding 4: SEC-FINDING-A11 — Numeric `-0` vs `+0` and Unicode Normalization Forms

- **Finding ID:** `SEC-FINDING-A11`
- **Severity:** Informational
- **Exact File & Lines:** [`scripts/planWbsRegistrationTransaction.ts#L160-L175`](../../scripts/planWbsRegistrationTransaction.ts#L160-L175)
- **Attack Conditions & Required Privileges:** Passing `-0` as a number or passing strings in different Unicode normalization forms (NFC vs NFD, e.g. `\u00E9` vs `e\u0301`).
- **Does Attack Actually Succeed?** **NO SECURITY IMPACT**.
  In JavaScript, `JSON.stringify(-0)` evaluates to `"0"`, so `-0` is canonically serialized as `"0"`. For Unicode strings, the preflight preserves raw UTF-8 code points without forced NFC conversion. As a result, NFC and NFD strings produce different hashes, preserving byte integrity rather than conflating distinct byte sequences.
- **Complete Reproducible Test Case:**
  ```typescript
  assert.equal(JSON.stringify(-0), "0");
  const sNFC = "caf\u00e9", sNFD = "cafe\u0301";
  assert.notEqual(Buffer.from(sNFC), Buffer.from(sNFD));
  ```
- **Expected vs Observed Result:** Deterministic byte hashing observed.
- **Stage B2b1 vs Unimplemented Integration:** General JavaScript serialization behavior.
- **Recommended Remediation:** Document in schema specification that all human-signed manifests must use UTF-8 NFC.
- **Merge-Blocking Status:** `NOT_MERGE_BLOCKING`.
- **Classification:** `ACCEPTABLE_BOUNDED_RISK`.

### Finding 5: SEC-FINDING-B08 — Historical WBS State Cycles in Ledger Parsing (Remediated in PR #39)

- **Finding ID:** `SEC-FINDING-B08`
- **Severity:** Medium (Pre-Fix Defect; Remediated in `parseLedger()`)
- **Exact File & Lines:** [`scripts/planWbsRegistrationTransaction.ts#L414-L443`](../../scripts/planWbsRegistrationTransaction.ts#L414-L443)
- **Pre-Fix Behavior (`9a7b52f` / `f1ab7f5`):**
  In the pre-fix implementation, `parseLedger()` checked only pairwise adjacency (`entry.preWbsSha256 === cursor && entry.postWbsSha256 !== cursor`) without tracking previously visited WBS state hashes across the ledger chain. When a ledger was constructed with `Genesis -> State X -> Genesis` (`entries: [forgedEntry, back]`), `parseLedger()` accepted the cyclic chain returning to `HISTORICAL_WBS_SHA256`, and a subsequent valid additive registration from `Genesis -> W1` previewed `VALID` (`mode: 'PREVIEW_VALID'`), because downstream `verifyTrustedWbsRegistrationV2` validates only the immediate `beforeBytes -> afterBytes` delta (`Genesis -> W1`) and does not inspect prior ledger entries. This pre-fix behavior is preserved in the historical execution log [`pr39_adversarial.log`](pr39_adversarial.log) (lines 49–50).
- **Remediation Applied:**
  Modified `parseLedger()` in [`scripts/planWbsRegistrationTransaction.ts`](../../scripts/planWbsRegistrationTransaction.ts) to initialize `const seenWbsStates = new Set<string>([HISTORICAL_WBS_SHA256])` and reject any ledger entry whose `postWbsSha256` repeats `HISTORICAL_WBS_SHA256` or any prior `postWbsSha256` with the explicit error:
  `"Receipt ledger chain contains a WBS state cycle or repeated WBS digest"`.
- **Complete Reproducible Test Case (Post-Correction):**
  ```typescript
  const back = {
    ...forgedEntry,
    receiptId: 'FORGED-HISTORY-0002',
    preWbsSha256: digest(Wforged),
    postWbsSha256: HISTORICAL_WBS_SHA256,
  };
  const Lc = serializeWbsReceiptLedger({
    ...makeHistoricalWbsReceiptLedger(),
    entries: [forgedEntry, back],
  });
  const r = previewWbsRegistrationTransaction({
    ...base1(),
    ledgerBytes: Lc,
    expectedCurrentLedgerSha256: digest(Lc),
    trustedContext: ctx(git1, ['FORGED-HISTORY-0001', 'FORGED-HISTORY-0002']),
  });
  assert.equal(r.valid, false);
  assert.equal(r.mode, 'REJECTED');
  assert.equal(r.mayApply, false);
  assert.ok(r.errors.some(e => e.includes('Receipt ledger chain contains a WBS state cycle or repeated WBS digest')));
  ```
- **Expected vs Observed Result (Post-Correction):**
  - *Expected:* Fail-closed rejection (`REJECTED`, `valid: false`, `mayApply: false`) with explicit cycle error while preserving valid consecutive additive chains (`Genesis -> W1 -> W2`).
  - *Observed:* Rejected fail-closed with `["Receipt ledger invalid: Receipt ledger chain contains a WBS state cycle or repeated WBS digest"]` in both `scripts/testPlanWbsRegistrationTransaction.ts` (check 26/26) and [`pr39_adversarial.post_b08_fix.log`](pr39_adversarial.post_b08_fix.log) (lines 49–50); valid consecutive additive registrations continue to succeed (check 23/26 and scenario C01).
- **Classification:** `FIXED_AND_VERIFIED`.

## 3. Review of All Five Known Limitations

The five confirmed limitations characterize the exact architectural boundary between Stage B2b1 (read-only advisory transaction preflight) and Stage B2b2 (production transactional execution).

| Ref ID | Limitation Scenario | Category (1–5) | Implementation Boundary & Consequence | Production Acceptance Determination |
|---|---|---|---|---|
| **LIMIT-01** | **D01: Self-Attested `trustedContext`** | **1** (Missing trusted human identity/policy enrollment) & **5** (Missing production controls) | Preflight takes `trustedContext` as an input argument. If a local caller generates their own keypair and supplies a matching `pinnedPolicySha256`, preflight returns `valid: true`. **Consequence:** Preflight confirms mathematical consistency relative to input context; it does not confer authorization authority. | **ACCEPTABLE FOR B2B1; PRODUCTION BLOCKER**. Acceptable for read-only planning. Production execution must anchor policy digests in protected branch configuration. `mayApply: false` invariant ensures no authority leak. |
| **LIMIT-02** | **C07: Absence of Atomic Compare-And-Swap (CAS)** | **3** (Atomic receipt consumption & replay) & **5** (Missing production controls) | Preflight is a stateless pure function. If PR #34 and a competing PR both run preflight against the same base master state, both return `valid: true` with conflicting proposed ledgers. **Consequence:** Preflight cannot serialize concurrent merges. | **ACCEPTABLE FOR B2B1; PRODUCTION BLOCKER**. Preflight plans candidate transitions; concurrency serialization belongs to Git branch merge locks and atomic CAS in Stage B2b2. |
| **LIMIT-03** | **B09: Stale Snapshot Replay** | **2** (Externally supplied Git provenance) & **3** (Atomic receipt consumption & replay) | If a caller feeds an outdated WBS snapshot and genesis ledger into preflight, an already-consumed receipt `R1` will preview `valid: true`. **Consequence:** Freshness depends entirely on the caller providing live protected branch HEAD state (`expectedCurrent*`). | **ACCEPTABLE FOR B2B1; PRODUCTION BLOCKER**. Preflight checks deltas relative to input baselines. Production CI runners must bind directly to verified `origin/master` HEAD. |
| **LIMIT-04** | **B07: Historical Ledger Entries Not Cryptographically Re-Verified** | **4** (Historical signature or receipt-chain authentication) | `parseLedger()` validates hash-chain continuity and byte-exact canonical formatting, but does not re-verify the Ed25519 signatures of historical ledger entries. **Consequence:** A forged historical entry with valid contiguous hashes is accepted structurally by preflight. | **ACCEPTABLE FOR B2B1; PRODUCTION BLOCKER**. Preflight verifies the candidate delta; complete historical auditability requires the Stage B2b immutable receipt store (`docs/07_verification/wbs-registration-receipts/<receiptId>.json`). |
| **LIMIT-05** | **A13: Duplicate Keys in Raw Receipt JSON Text** | **5** (Other missing production controls) | `previewWbsRegistrationTransaction` accepts an already-parsed JavaScript object. If an upstream caller parsed JSON using a parser that allowed duplicate keys, preflight sees only the parsed representation (last-wins). | **ACCEPTABLE FOR B2B1; PRODUCTION BLOCKER**. Preflight operates on in-memory contracts. Stage B2b2 write engine must accept raw UTF-8 `Buffer` bytes with canonical deduplication. |
