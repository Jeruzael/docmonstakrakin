## Implemented core contract

`WorkspaceStore.open(root, {initialize:true, actionReceipts:true})` explicitly creates a new schema2 authority. Omitted opt-in retains schema1. Existing authorities reject the opt-in before opening SQLite, even if already schema2; neither schema is migrated. Normal open discovers either exact admitted schema. Schema2 provenance is `WORKSPACE_AUTHORITY/2`, and only its snapshot response adds `actionReceipts:true`.

Schema2 adds nullable `operations.receiptJson` with a 4096 UTF-8 byte SQL constraint. Legacy `commit` writes a null tombstone and retains duplicate rejection on both schemas. `commitReceipt` additionally binds the request hash and original requested project scope; it atomically persists the snapshot, operation row, fixed-field canonical receipt and audit events. The receipt records the stable actor, action, requested/actual project, request/effect hashes and committed revisions. It has no session token, credential or original response body.

`lookupReceipt` requires a valid current session and exact operation/actor/action/request/scope binding. It rechecks current action permission and read permission on the actual affected project, including a newly created target. Unknown authorized operations return null; legacy tombstones and mismatched requests reject. Exact duplicate receipt commits additionally require the original effect hash. A returned acknowledgment is historical; later work does not change its committed revision. Restart, logout, disable and membership rules remain the existing authority rules.

Reopen validates exact SQL, bounded canonical receipt fields, operation/revision links, existing principal/project, current-latest effect hash, the original snapshot audit event, and the receipt's audit hash commitment. Receipt removal cannot turn an acknowledged operation into a legacy tombstone without leaving a rejected orphan commitment. This is local consistency under the existing private-store custody model; a same-account adversary rewriting the whole coherent database/audit chain is not independently witnessed or prevented by these hashes.

## Audit decision and compatibility

The coordinating agent accepted an additional `ACTION_RECEIPT_COMMITTED` event whose existing `targetHash` field commits the canonical receipt JSON. The original `PROJECT_SNAPSHOT_COMMITTED` event remains. Both use the unchanged six-field audit serialization and share the transaction, time, generation and revisions.

Each new receipt commit therefore consumes **two audit rows**. Lookup and exact replay append **zero** rows. The 4096-row ceiling and all timeouts/permissions remain unchanged. With only one free audit slot, failure at the second event rolls back the snapshot, ownership, operation, receipt, first event and clock advancement. This is not a capacity remedy.

Old code rejects schema2. Existing backup/restore and the separate capacity inspector initially reject it as unsupported; no downgrade or valuable-state migration is qualified. Legacy schema1 replay and exact SQL behavior remain intact. The parent HTTP review identified the dynamic package-import action-classification problem; the integrator chose to exclude protocol1 on that route while retaining legacy import, rather than relax action equality.
