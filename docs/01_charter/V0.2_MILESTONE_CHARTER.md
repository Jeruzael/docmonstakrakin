# docmonstakrakin v0.2 Milestone Charter
## Planning Charter: Team Collaboration, Secure Cloud Sync & Multi-Agent Gateways

**Document ID:** CHARTER-V02-001  
**Milestone:** `v0.2 Connected Governance & Team Workspaces`  
**Status:** `DRAFT / PLANNING ONLY` (Pending Human Stakeholder Ratification)  
**Target Delivery Window:** Q1 2027  
**Previous Baseline:** `v0.1.0-rc1` (Technically Verified Release Candidate; Gate 7 Human Sign-off Pending)  

---

### 1. Problem Statement
docmonstakrakin v0.1 successfully established an isolated, local-first control plane with zero-trust path boundaries, sandboxed command execution, and cryptographic audit hashing for single-developer environments. However, software engineering in enterprise and open-source settings requires multi-developer coordination, distributed agent assistance, and seamless synchronization across developer workstations without sacrificing local-first autonomy, data sovereignty, or zero-trust boundaries.

### 2. Goals
1. Provide cross-workstation synchronization for project state, requirements, ADRs, and audit ledgers.
2. Enable multi-agent and multi-human collaboration on unified work items without race conditions.
3. Preserve strict local-first autonomy: full offline read/write capabilities with zero cloud lock-in.
4. Enforce end-to-end zero-knowledge encryption so untrusted transport relays cannot inspect project data or secrets.
5. Provide optional self-hosted and user-managed backend connectors alongside standard local storage.

### 3. Explicit Non-Goals
1. **No Cloud-Only Dependency:** The system MUST NOT require an active internet connection or remote account for core development operations.
2. **No Remote Secret Storage:** Private provider keys (`GEMINI_API_KEY`, personal access tokens) MUST NEVER be synchronized across devices or stored in remote sync relays.
3. **No Unbounded Real-Time Collaborative Canvas:** Not building a generic rich-text editor or Google Docs clone; collaboration is scoped strictly to structured SSDLC artifacts (requirements, risks, work items, ADRs, audit events).
4. **No Centralized Server Authority Over Local Truth:** The local workstation repository remains sovereign; remote gateways act as peer relays, not totalitarian dictators.

### 4. Candidate Capabilities
- **`CAP-v02-01` (Encrypted State Sync Gateway):** Asynchronous delta synchronization over WebSocket/HTTPS with end-to-end payload encryption.
- **`CAP-v02-02` (Multi-Agent Team Identities):** Ed25519 cryptographic identity pairing for team members and specialized autonomous sub-agents.
- **`CAP-v02-03` (Multi-Writer Merkle DAG Audit Ledger):** Distributed audit log reconciliation allowing multiple concurrent signers without chain breakage.
- **`CAP-v02-04` (Non-Destructive Conflict Resolution Engine):** Three-way semantic merge for SSDLC records with explicit manual reconciliation for divergent requirements.
- **`CAP-v02-05` (External Issue Tracker Synchronization):** Bi-directional synchronization bridge to GitHub Issues / Jira for workitem projections.
- **`CAP-v02-06` (Self-Hosted Sync Relay Docker Image):** Lightweight, zero-knowledge relay service for air-gapped enterprise deployments.

### 5. User & Persona Impact
- **Security Lead:** Gains cross-team visibility into SSDLC gate compliance and audit trails without needing direct filesystem access to developer laptops.
- **Lead Architect:** Can collaborate synchronously on ADR proposals with cryptographic co-signatures.
- **Developer / Agent Operator:** Works completely offline while travelling; changes automatically merge cleanly upon reconnecting.
- **Autonomous Agent:** Receives scoped workitem assignments with verifiable origin tokens and strict output sandboxing.

### 6. Local-First Compatibility Requirements
- All reads, writes, audits, prompt compilations, and command sandboxes continue to execute locally with zero network calls when offline.
- Divergent offline edits are queued in an append-only local mutation log (`.docmonstakrakin/outbox/`).
- Network failures or remote server downtime must result in transparent fallback to local mode with zero user-facing error dialogs blocking development.

### 7. Security & Privacy Implications
- **Zero-Knowledge Transport:** The sync relay sees only ciphertext envelopes encrypted with the project team's shared symmetric key (derived via Argon2id / X25519).
- **Data Classification Preservation:** Confidential and Restricted project metadata cannot be exported to public or unverified sync relays.
- **Zero Remote Secrets:** SecretStore entries are explicitly tagged with local device affinity and excluded from synchronization envelopes.

### 8. Trust-Boundary Changes
- **v0.1 Boundary:** Single local machine; trust boundary separates host container from filesystem sandbox and model inference proxy.
- **v0.2 Boundary Expansion:** Introduces two new trust zones:
  1. *Untrusted Network Relay Zone (Cloud/WAN):* Zero trust assumed; transport security guaranteed strictly by end-to-end cryptographic envelopes.
  2. *Collaborator Peer Zone:* Peer workstations have varying privileges; peer signatures must be validated before merging mutations into local canonical state.

### 9. Data-Model Implications
- Requirement, Risk, and WorkItem schemas must introduce:
  - `vectorClock: Record<string, number>` for causal ordering.
  - `originAuthorId: string` and `authorSignature: string` (Ed25519).
  - `tombstone: boolean` and `deletedAt?: string` to support distributed deletes without resurrection.
- Audit ledger transitions from a linear linked list to a **Merkle Directed Acyclic Graph (DAG)** with multiple parent hashes.

### 10. Deployment Implications
- Core web application continues to operate in standard container environments (e.g. Cloud Run, standalone desktop web).
- Optional sync relay server deployed as a minimal Go/Rust or Node microservice with SQLite/Postgres persistence for encrypted blobs.

### 11. Migration & Backward-Compatibility Implications
- Existing v0.1 `.docmonstakrakin` package archives must remain 100% importable and exportable without schema loss.
- Linear audit ledgers from v0.1 represent the root trunk of the v0.2 Merkle DAG.

### 12. External-Service Dependencies
- Optional relay service endpoint (user-configured).
- Optional Git remote repository (via standard SSH/HTTPS git protocols).
- Zero mandatory proprietary SaaS dependencies.

### 13. Agent-Permission Implications
- Autonomous agents acting on shared projects must possess cryptographically verifiable agent certificates signed by a human project owner.
- Agents cannot self-assign permissions or approve human-gated phase transitions (preserving SEC-CTRL-020).

### 14. Major Technical Risks
- **`RISK-020` (Concurrent Mutation Race Conditions):** Conflicting requirement approvals causing divergent SSDLC states.
- **`RISK-021` (Remote Relay Compromise):** Compromised relay attempts replay attacks or selective withholding of security updates.
- **`RISK-022` (Key Management & Peer Eviction):** Revoking a departed team member's access without forcing complete project re-encryption.
- **`RISK-023` (Cross-Agent Prompt Injection):** Malicious collaborator injects adversarial instructions into shared work item descriptions.

### 15. Open Decisions
- Conflict Resolution Mechanism: State-based CRDTs vs Delta-based Operational Transformation vs Deterministic 3-Way Merge (Documented as Preferred Candidate in proposed ADR-0005).
- Multi-Agent Identity Protocol: Decentralized Identifiers (DIDs) vs X.509 certificates vs Simple Ed25519 Public Key Ledger (Documented as Preferred Candidate in proposed ADR-0006).

### 16. Human Decisions Required
1. **Scope Ratification:** Approval of candidate capabilities for v0.2.
2. **Sync Architecture Decision:** Review and ratification of proposed ADR-0005 (Preferred Candidate: Hybrid 3-Way Merge + Merkle DAG).
3. **Identity & Key Management Decision:** Review and ratification of proposed ADR-0006 (Preferred Candidate: Ed25519 Peer Keyring with Scoped Delegation).
4. **Relay Hosting Model:** Review and choice of reference relay deployment model (Self-hosted only vs Hosted multi-tenant preview).

### 17. Proposed Success Criteria
- 100% offline functionality verified under simulated network disconnection.
- Zero plaintext leak of requirements or secrets over simulated untrusted sync relay.
- Deterministic convergence of 10 concurrent conflicting edits across 3 simulated peer nodes.
- Full roundtrip backward-compatibility with v0.1 `.docmonstakrakin` packages.
